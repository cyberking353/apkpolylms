================================================================================
AL-HIKMA POLYTECHNIC — STUDENT MANAGEMENT SYSTEM (SMS) <-> LMS INTEGRATION
API CONTRACT (v1.0)
================================================================================
Prepared for: SMS developer
From:         Al-Hikma LMS team

--------------------------------------------------------------------------------
1. PURPOSE & DATA FLOW
--------------------------------------------------------------------------------
The Student Management System (SMS) is the SINGLE SOURCE OF TRUTH for student
identity and enrollment data (matric number, name, email, department, level,
current session, courses). The LMS never creates student accounts by hand —
it RECEIVES them from the SMS and mirrors them.

Direction of data:
  SMS  ---(push or pull)-->  LMS

  Student logs into the SMS portal  ->  LMS account is created/updated  ->
  LMS enrolls them in the correct courses automatically.

There is NO student self-registration on the LMS, and no LMS-only student
records. Every student record on the LMS originates from the SMS.

--------------------------------------------------------------------------------
2. AUTHENTICATION (how the LMS authenticates to the SMS)
--------------------------------------------------------------------------------
The LMS calls the SMS using an API token.

  Header:  Authorization: Bearer <API_TOKEN>
  Content-Type: application/json

- The SMS issues one long-lived token for the LMS to use. Treat it as a
  shared secret. Revoke/rotate it from the SMS side if compromised.
- All endpoints must be HTTPS in production.

--------------------------------------------------------------------------------
3. ENDPOINT 1 — FETCH ALL STUDENTS (pull / on-demand sync)
--------------------------------------------------------------------------------
Used for the initial bulk load and for manual "sync now" runs.

REQUEST
  GET  /api/v1/students
  Authorization: Bearer <API_TOKEN>

Optional query filters (all optional):
  ?session=2025/2026        Only students in this session
  ?updated_since=2026-08-01T00:00:00Z   Only students updated since a timestamp (for incremental sync)

RESPONSE 200 OK
{
  "session": "2025/2026",
  "count": 3,
  "students": [
    {
      "matric_number": "CS/ND1/001",
      "first_name": "Amina",
      "last_name": "Bello",
      "email": "cs.nd1@demo.alhikma",
      "department_code": "CS",
      "academic_level": "ND1",
      "current_session": "2025/2026",
      "semester": "2",
      "status": "active",
      "course_codes": ["COM101", "MTH101", "BUS101"]
    },
    {
      "matric_number": "EE/ND1/001",
      "first_name": "Yusuf",
      "last_name": "Sani",
      "email": "ee.nd1@demo.alhikma",
      "department_code": "EE",
      "academic_level": "ND1",
      "current_session": "2025/2026",
      "semester": "2",
      "status": "active",
      "course_codes": ["EEC101", "MTH101"]
    }
  ]
}

Field dictionary (see section 5 for the full table):
  matric_number    string  UNIQUE identifier (the join key — never changes)
  first_name       string  Required
  last_name        string  Required
  email            string  Required, must be unique in the SMS
  department_code  string  Must match a department code the LMS knows (section 6)
  academic_level   string  One of ND1, ND2, HND1, HND2 (section 7)
  current_session  string  e.g. "2025/2026" (the school year the student is in)
  semester         string  "1" or "2"
  status           string  "active" | "inactive" | "graduated" (section 8)
  course_codes     array   Course codes the student is registered for this session

--------------------------------------------------------------------------------
4. ENDPOINT 2 — UPSERT A SINGLE STUDENT (push / real-time)
--------------------------------------------------------------------------------
The SMS calls the LMS when a student is created or edited, so the LMS updates
immediately instead of waiting for the next full sync.

REQUEST
  POST /api/v1/sync/students
  Authorization: Bearer <LMS_API_TOKEN>
  Content-Type: application/json

BODY
{
  "matric_number": "CS/ND1/002",
  "first_name": "Fatima",
  "last_name": "Usman",
  "email": "cs.nd1.002@demo.alhikma",
  "department_code": "CS",
  "academic_level": "ND1",
  "current_session": "2025/2026",
  "semester": "2",
  "status": "active",
  "course_codes": ["COM101", "MTH101"]
}

UPSERT SEMANTICS (important):
- If a student with this matric_number already exists on the LMS, UPDATE the
  record (overwrite fields above).
- If not, CREATE it.
- Re-sending the same payload is safe and idempotent (no duplicates, no error).
- course_codes is optional. If omitted, the LMS derives enrollment from
  department + level + session (see section 9). If provided, it overrides.

RESPONSE 201 CREATED  (new student)
{
  "ok": true,
  "created": true,
  "matric_number": "CS/ND1/002"
}

RESPONSE 200 OK  (existing student updated)
{
  "ok": true,
  "created": false,
  "matric_number": "CS/ND1/002"
}

--------------------------------------------------------------------------------
5. FULL FIELD DICTIONARY (applies to all endpoints)
--------------------------------------------------------------------------------
FIELD             TYPE     REQUIRED  NOTES
--------------------------------------------------------------------------------
matric_number     string   YES       Unique across the whole SMS. NEVER changes
                                     for the life of the student. This is the
                                     primary join key between SMS and LMS.
first_name        string   YES       Student's first name.
last_name         string   YES       Student's surname.
email             string   YES       Must be a valid email, unique in the SMS.
department_code   string   YES       Short code, e.g. "CS". Must be a code the
                                     LMS knows (section 6).
academic_level    string   YES       "ND1","ND2","HND1","HND2" (section 7).
current_session   string   YES       School year, e.g. "2025/2026". Drives which
                                     courses/semester the student sees.
semester          string   NO        "1" or "2". If missing, LMS uses its own
                                     current-semester setting.
status            string   NO        "active" (default), "inactive", "graduated".
                                     Inactive/graduated students can no longer
                                     log in to the LMS.
course_codes      array    NO        List of course codes (strings). Optional —
                                     see section 9 for how enrollment works.

--------------------------------------------------------------------------------
6. DEPARTMENT CODES (department_code allowed values)
--------------------------------------------------------------------------------
The SMS MUST send one of these codes (case-sensitive, upper-case). The LMS
currently knows these departments:

  CS    Computer Science
  EE    Electrical Engineering
  ME    Mechanical Engineering
  BA    Business Administration
  BUS   Business Administration   (see note below)
  SLT   Science Laboratory Technology
  ACC   Accountancy
  MC    Mass Communication
  OTH   Other

NOTE: "BA" and "BUS" currently both map to "Business Administration" in the
LMS seed data. The SMS should standardise on ONE code (recommended: CS, EE,
ME, BA, SLT, ACC, MC, OTH) and send it consistently. If a department code is
unknown to the LMS, the sync should still store the student but flag the
department for manual review — it must NOT fail the whole batch.

--------------------------------------------------------------------------------
7. ACADEMIC LEVELS (academic_level allowed values)
--------------------------------------------------------------------------------
  ND1   ND Year 1
  ND2   ND Year 2
  HND1  HND Year 1
  HND2  HND Year 2

--------------------------------------------------------------------------------
8. STATUS VALUES
--------------------------------------------------------------------------------
  active    Default. Student can log in and sees their courses.
  inactive  Student cannot log in (account disabled).
  graduated Student has completed; account kept for records, login disabled.

--------------------------------------------------------------------------------
9. ENROLLMENT (how courses are assigned)
--------------------------------------------------------------------------------
Two supported modes:

A) SMS-DRIVEN (recommended once SMS is authoritative for registration):
   The SMS sends course_codes in the payload. The LMS enrolls the student in
   exactly those courses (matching by the course's code field in the LMS,
   e.g. COM101). Course codes not found in the LMS are skipped and logged.

B) LMS-DERIVED (current behaviour, used when course_codes is omitted):
   The LMS auto-enrolls based on department + academic_level + the school-wide
   current semester (AcademicSettings singleton). No course list needed.

Recommendation: start with mode B, then switch to mode A once the SMS course
registration is final. This gives a working system immediately without the
SMS needing to maintain perfect course-code parity.

--------------------------------------------------------------------------------
10. ERROR RESPONSES (shared format)
--------------------------------------------------------------------------------
The LMS should respond with JSON and proper HTTP status codes:

  400 Bad Request    Missing required field / invalid value
  401 Unauthorized   Missing or invalid API token
  422 Unprocessable  Payload valid JSON but violates a rule (e.g. unknown
                     department_code)
  500 Server Error   Internal error on the LMS side

Error body:
{
  "ok": false,
  "error": "human-readable message",
  "field_errors": { "department_code": "Unknown department code" }   // optional
}

--------------------------------------------------------------------------------
11. RECOMMENDED SYNC SCHEDULE
--------------------------------------------------------------------------------
1. Initial:  one-time full GET /api/v1/students load.
2. Ongoing:   SMS pushes POST /api/v1/sync/students on every create/edit
              (recommended, gives real-time updates).
3. Safety:    A nightly full re-sync (GET) as a reconciliation pass to catch
              any missed pushes. Idempotent, so re-running is harmless.

--------------------------------------------------------------------------------
12. OPTIONAL FUTURE — SSO (single sign-on)
--------------------------------------------------------------------------------
Not required for v1. Later, to remove LMS passwords entirely:
  - SMS issues a signed, short-lived token after the student logs into the SMS.
  - Student clicks "Open LMS" -> redirected to LMS with the token.
  - LMS validates the token, upserts the student, and logs them in.
Design this only after the sync API above is stable.

--------------------------------------------------------------------------------
13. CONTACT / OWNERSHIP
--------------------------------------------------------------------------------
- SMS team owns:  /api/v1/students endpoint, issuing the API token, keeping
                  student data accurate.
- LMS team owns:  /api/v1/sync/students endpoint, idempotent upsert logic,
                  enrollment mapping, login-by-matric support.
- Agreement: matric_number is the single join key and must never change.
