LMS Database Schema Recommendations

Here is a breakdown of the core database tables/collections the LMS developer should create, along with the specific fields they need to store the data coming from the Portal.

I've marked the primary keys and the fields they should use to link records together.

1. Users Table (Students & Staff)

This table stores all accounts that can log into the LMS.

  • id (Primary Key): The LMS's own internal ID.
  • portal_id (Unique/Indexed): The UUID coming from the Portal's id or sub field. This is the most important field for linking LMS users to Portal users.
  • email: User's email address (used in SSO).
  • first_name: First name.
  • last_name: Last name.
  • user_type: Enum string ("student" or "staff").
  • matric_number: (Nullable) Student matriculation number.
  • staff_id: (Nullable) Staff identification code.
  • department_code: (Nullable) The short code of their department (e.g., CSC).
  • academic_level: (Nullable) Derived string level (e.g., ND1, HND2).
  • current_session: (Nullable) E.g., 2024/2025.
  • semester: (Nullable) "1" or "2".
  • status: e.g., "active", "suspended".
  • lms_access: Boolean. If false, the LMS should block them from logging in.

2. Courses Table

This table stores the master list of all courses.

  • id (Primary Key)
  • course_code (Unique/Indexed): e.g., CSC101. This is what links registrations to courses.
  • title: Course title.
  • credit_unit: Integer.
  • description: (Nullable) Text description.
  • offerings: Array/JSON of objects. Contains programme_code, department_code, level, semester, and is_elective.
  • lecturers: Array/JSON of objects. Contains staff_id, first_name, and last_name.

3. Departments Table

  • id (Primary Key)
  • portal_id (Unique/Indexed): UUID from the Portal.
  • code (Unique/Indexed): Short code (e.g., CSC). Used to link Students and Programmes to this department.
  • name: Full name (e.g., "Computer Science").
  • is_active: Boolean.

4. Programmes Table

  • id (Primary Key)
  • portal_id (Unique/Indexed): UUID from the Portal.
  • code (Unique/Indexed): Short code (e.g., NDCSC).
  • name: Full name.
  • department_code: Links back to the Department table's code.
  • programme_type: String (e.g., "NATIONAL_DIPLOMA").
  • duration: Integer (years).
  • is_active: Boolean.

5. Academic Sessions Table

  • id (Primary Key)
  • portal_id (Unique/Indexed): UUID from the Portal.
  • name (Unique/Indexed): e.g., "2024/2025".
  • start_date: Timestamp/Date.
  • end_date: Timestamp/Date.
  • is_current: Boolean (Only one session should be current at a time).
  • is_active: Boolean.

6. Course Registrations Table

This table maps a student to the courses they are taking in a specific session/semester.

  • id (Primary Key)
  • portal_id (Unique/Indexed): UUID from the Portal.
  • student_matric (Indexed): Links back to the User table's matric_number.
  • academic_session: Links to the Session table's name (e.g., "2024/2025").
  • semester: "1" or "2".
  • level: Integer (e.g., 100, 200).
  • courses: Array/JSON of course objects. E.g., [{ course_code: "CSC101", is_carried_over: false }]. This links to the Courses table.
  • status: e.g., "SUBMITTED".

[!TIP] A Note for the Developer: For simple setup, the offerings, lecturers, and registered courses arrays can just be stored as JSON columns in your database. However, if you are using a relational database (like PostgreSQL or MySQL) and want strict integrity, you can split those arrays out into join tables (e.g., a CourseLecturer table and a StudentEnrolledCourse table).

Regardless of how you structure the underlying SQL, the fields above represent the exact JSON data you will receive from the Portal's webhooks.
