Al-Hikma Portal ↔ LMS Integration Guide

Audience: The LMS developer. This document contains everything you need to integrate with the Al-Hikma SMS/Portal.

1. Architecture Overview

graph LR
  subgraph Portal ["SMS/Portal (System of Record)"]
    A[Student Portal<br/>:3001]
    B[Admin Portal<br/>:3000]
    C[Portal Backend<br/>:5000]

  E -- "3. Sends JWT to backend for verification" --> D
  D -- "4. Verifies JWT, creates session" --> E

  C -- "Server-to-server sync (Bearer token)" --> D

Key Principles

Principle Detail
Portal = Source of Truth The Portal owns student identity, academic data, and official results. The LMS never creates or modifies this data.
LMS = Learning Delivery The LMS consumes synced data and manages courses, content, submissions, and learning progress.
Async Sync Student/course data is pushed from Portal → LMS via server-to-server API calls. The LMS must expose the endpoints described below.
SSO (Portal → LMS) Students and staff authenticate through the Portal. The LMS receives a signed JWT assertion and creates its own session. The LMS must NOT maintain independent Portal passwords.

2. Shared Secrets & Configuration

You will receive two secrets from the Portal admin. Never expose these in frontend code or version control.

Variable Purpose Example
PORTAL_SSO_SECRET HMAC-SHA256 shared secret for verifying SSO JWT assertions. Must match the Portal's LMS_SSO_SECRET. c7c5a0fd... (256-char hex)
LMS_API_TOKEN Bearer token the Portal uses when calling your sync endpoints. Your backend must validate this on every sync request. Must match the Portal's LMS_API_TOKEN. b2df3a34... (128-char hex)

Your Environment Variables

# Shared secret for verifying Portal SSO assertions
PORTAL_SSO_SECRET=<value from Portal admin>

# Bearer token that the Portal will send on sync requests
LMS_API_TOKEN=<value from Portal admin>

# Your LMS URLs
LMS_BACKEND_URL=http://localhost:4000
LMS_FRONTEND_URL=http://localhost:4001

3. SSO Authentication Flow

3.1 How It Works

sequenceDiagram
  participant Browser
  participant Portal as Portal Backend (:5000)
  participant LmsFE as LMS Frontend (:4001)
  participant LmsBE as LMS Backend (:4000)

  Browser->>Portal: GET /api/v1/lms/sso (with session cookie)
  Portal->>Portal: Verify session, check eligibility
  Portal->>Portal: Sign JWT with PORTAL_SSO_SECRET
  Portal-->>Browser: 302 Redirect → LMS_FRONTEND_URL/sso/callback?assertion=<jwt>
  Browser->>LmsFE: GET /sso/callback?assertion=<jwt>
  LmsFE->>LmsBE: POST /api/v1/auth/sso { assertion: "<jwt>" }
  LmsBE->>LmsBE: Verify JWT signature & expiry
  LmsBE->>LmsBE: Find-or-create user in LMS database
  LmsBE-->>LmsFE: 200 OK { user, session_token }
  LmsFE->>LmsFE: Store session, redirect to dashboard

3.2 JWT Assertion Structure

The Portal signs a JWT using HMAC-SHA256 (HS256) with the shared PORTAL_SSO_SECRET. The JWT has a 60-second TTL (configurable).

Student Assertion Payload

{
  "sub": "fbba8d1d-bd55-4ddc-b978-36ce979c841f",
  "matric_number": "AHP/ND/CSC/24/0042",
  "email": "student@example.com",
  "first_name": "Amina",
  "last_name": "Bello",
  "user_type": "student",
  "iat": 1723454400,
  "exp": 1723454460
}

Staff Assertion Payload

{
  "sub": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "staff_id": "STAFF001",
  "email": "lecturer@example.com",
  "first_name": "Dr. Ibrahim",
  "last_name": "Musa",
  "user_type": "staff",
  "iat": 1723454400,
  "exp": 1723454460
}

Field Reference

Field Type Present In Description
sub string (UUID) Both Unique Portal ID for this student/staff record. Use this as the primary key to link Portal ↔ LMS users.
matric_number string Student only Official matriculation number (e.g. AHP/ND/CSC/24/0042).
staff_id string Staff only Staff ID code.
email string Both User's email address.
first_name string Both First name.
last_name string Both Last name.
user_type "student" | "staff" Both Discriminator for the user type.
iat number Both Issued-at timestamp (Unix epoch seconds).
exp number Both Expiry timestamp (Unix epoch seconds). Default: iat + 60.

3.3 What You Must Implement

Your LMS backend must expose an endpoint that:

  1. Receives the JWT assertion (from your frontend or directly).
  2. Verifies the JWT signature using PORTAL_SSO_SECRET with algorithm HS256.
  3. Checks exp has not passed (JWT is not expired).
  4. Uses sub to find-or-create a user in your LMS database.
  5. Creates an LMS session/token for the user.
  6. Returns the session to your frontend.

[!WARNING] The JWT is single-use and short-lived (60 seconds). It is only for authentication. After verification, create your own LMS session. Do NOT use the JWT as a session token.

3.4 Endpoint Spec: SSO Verification (Hosted on your LMS)

POST <LMS_BACKEND_URL>/api/v1/auth/sso
Content-Type: application/json

{
  "assertion": "<jwt_string>"
}

Success Response (200):

{
  "success": true,
  "user": {
    "id": "local-lms-user-id",
    "portal_id": "fbba8d1d-bd55-4ddc-b978-36ce979c841f",
    "email": "student@example.com",
    "first_name": "Amina",
    "last_name": "Bello",
    "user_type": "student",
    "matric_number": "AHP/ND/CSC/24/0042"
  },
  "token": "<your-lms-session-token>"
}

Error Response (401):

{
  "success": false,
  "message": "Invalid or expired assertion"
}

4. Server-to-Server Sync API

The Portal pushes data to the LMS asynchronously. Your backend must expose the following endpoints. All sync requests include a Bearer token in the Authorization header.

4.1 Authentication for Sync Endpoints

Every sync request from the Portal includes:

Authorization: Bearer <LMS_API_TOKEN>
Content-Type: application/json

Your middleware must validate this token on all /api/v1/sync/* endpoints. Reject with 401 if the token is missing or invalid.

4.2 Student Sync

POST <LMS_BACKEND_URL>/api/v1/sync/students

When it fires: The Portal sends this when:

  • A new student is enrolled (admission → student record)
  • A student's matric number is assigned (matriculation)
  • A student's profile is updated (name, phone, etc.)
  • A student's status changes (active → suspended, etc.)
  • A student is promoted to the next academic level
  • Nightly reconciliation (all online students re-synced at 4:00 AM)

Request Body:

{
  "matric_number": "AHP/ND/CSC/24/0042",
  "first_name": "Amina",
  "last_name": "Bello",
  "email": "student@example.com",
  "department_code": "CSC",
  "academic_level": "ND1",
  "current_session": "2025/2026",
  "semester": "1",
  "status": "active",
  "lms_access": true
}

Field Reference:

Field Type Description
matric_number string | null Unique matric number. May be null if not yet assigned (newly enrolled).
first_name string Student's first name.
last_name string Student's last name.
email string Student's email (also used in SSO).
department_code string Short code for the department (e.g. CSC, ACC).
academic_level string Derived level: ND1, ND2, HND1, HND2.
current_session string Academic session name (e.g. 2025/2026).
semester "1" | "2" Current semester number.
status string One of: active, suspended, withdrawn, expelled, graduated, inactive.
lms_access boolean Whether this student should have LMS access. false = disable login.

Expected Response (200):

{
  "success": true,
  "message": "Student synced successfully"
}

Your implementation should:

  • Use email or matric_number as the unique key to find-or-create the student.
  • Update all fields on subsequent syncs (upsert behavior).
  • When lms_access is false or status is not active, disable the student's LMS account.

Field Type Description

4.8 Initialization APIs (Hosted on the Portal)

If your LMS database is empty, you can bootstrap it by pulling the latest active data directly from the Portal. You must provide the LMS_API_TOKEN as a Bearer token.

Base URL: <PORTAL_BACKEND_URL>/api/v1/lms/sync/init

  • GET /departments — Fetch all active departments.
  • GET /programmes — Fetch all active programmes.
  • GET /sessions — Fetch all sessions.
  • GET /courses — Fetch all active courses.
  • GET /students — Fetch all active online students.
  • GET /registrations — Fetch all submitted course registrations.

Example:

GET <PORTAL_BACKEND_URL>/api/v1/lms/sync/init/departments
Authorization: Bearer <LMS_API_TOKEN>

5. Nightly Reconciliation

Every night at 4:00 AM, the Portal re-syncs all online students to the LMS by calling POST /api/v1/sync/students for each student. This ensures data consistency even if individual sync events were missed.

Your LMS should handle these as upserts — if the student already exists with the same data, it should be a no-op.

6. Error Handling

Sync Error Responses

If your endpoint encounters an error, return an appropriate HTTP status:

Status When
200 Success.
400 Invalid payload (missing required fields).
401 Invalid or missing Authorization token.
409 Conflict (e.g. duplicate matric number in an unexpected state).
500 Internal server error.

The Portal uses BullMQ (a job queue) for sync operations. Failed sync jobs will be automatically retried with exponential backoff. If your endpoint returns a 5xx error, the Portal will retry the request.

SSO Error Handling

Scenario What to do
No assertion query param Show "No assertion provided" error page.
JWT signature verification fails Show "Invalid assertion" error page.
JWT is expired (exp < now) Show "Assertion expired, please try again from the Portal" error page.
user_type is invalid Show "Unsupported user type" error page.

7. Quick-Start Checklist

  • Get secrets from Portal admin: PORTAL_SSO_SECRET and LMS_API_TOKEN.
  • Set up env vars as shown in Section 2.
  • Implement SSO verification endpoint POST /api/v1/auth/sso.
  • Implement initialization script to fetch bootstrap data (GET /api/v1/lms/sync/init/*)
  • Implement student sync endpoint POST /api/v1/sync/students.
  • Implement course sync endpoint POST /api/v1/sync/courses.
  • Implement department sync endpoint POST /api/v1/sync/departments.
  • Implement programme sync endpoint POST /api/v1/sync/programmes.
  • Implement session sync endpoint POST /api/v1/sync/sessions.
  • Implement registration sync endpoint POST /api/v1/sync/registrations.
  • Add auth middleware to validate LMS_API_TOKEN on all /api/v1/sync/* routes.
  • Build SSO callback page at /sso/callback on your frontend.
  • Test end-to-end: Login to student portal → Click "Open LMS" → Verify SSO lands on your dashboard.
